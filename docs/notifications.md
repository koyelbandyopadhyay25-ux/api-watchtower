## Monitoring and incident architecture

The existing secure HTTPS fetcher and schema engine are unchanged. After an actual `CheckResult` is written, `monitoring-service.ts` calls `store.notifications.observe` under the **same endpoint lock and PostgreSQL transaction**. Incident transitions, notification events, optional email-outbox creation, check/schema-change records and scheduled due advancement therefore commit together or roll back together. SMTP is never called inside this monitoring transaction. Unclaimed endpoints do not create user notifications.

There is one open incident per endpoint and kind, enforced both by the existing endpoint lock and a PostgreSQL partial unique index:

| Observation | Persisted behavior |
| --- | --- |
| First HTTP/network/JSON failure | Open availability incident; record one failure event |
| Further failures in that incident | Save real checks; no repeated failure emails, even if error category changes |
| Next valid JSON response | Close availability incident and record recovery; schema evaluation is independent |
| Differences against an accepted baseline | Open schema incident; record observed schema-change event |
| Identical structural differences | No duplicate schema event/email |
| Different structural differences while open | Update the canonical fingerprint and record the new observation |
| Successful comparison matching baseline | Close schema incident; label it “sample matches baseline,” not guaranteed compatibility |
| Explicit baseline acceptance | Close any open schema incident with `baseline_accepted`; do not invent endpoint recovery |

An explicit baseline-capture check can record actual differences against the previous baseline before the confirmed acceptance resolves the incident. Historical event text still describes that recorded check. Baselines are never automatically replaced. Failed checks and baseline-missing responses cannot establish schema restoration. Fingerprints canonicalize paths, change kinds and type sets, ignoring field/type ordering. Ordinary value changes still follow the existing comparison engine and do not become structural events.

Incidents/events are recorded for new owned checks even with notifications disabled. **No historical checks are replayed or backfilled.** Email is queued only if the endpoint's persisted preference is enabled when that transition is recorded. Enabling during an already observed ongoing failure does not replay its old opening alert; future recovery or new incidents may be queued. This avoids inventing a past onset time or sending historical mail.

## Outbox and dispatcher

`EmailOutbox` has one row per queued event. `EmailAttempt` records claims, start/finish timestamps, safe outcomes and error categories; it never stores raw SMTP errors or message bodies.

`notifications/main.ts` is a separate explicitly opted-in process. A short PostgreSQL claim transaction uses a dedicated advisory gate, row locks with `SKIP LOCKED`, a random lease token and 60-second expiry. It bounds **active leases across dispatchers to two**, increments the attempt count and creates an in-progress attempt before returning the committed job. The dispatcher rechecks preference and current endpoint ownership, then performs SMTP **outside every database transaction**. A short compare-and-set acknowledgement using the lease token commits acceptance, retry, cancellation or failure and the attempt record together.

SMTP operations have an absolute 8-second deadline with socket destruction, plus shorter connection/greeting/idle limits. Retryable errors use persisted 30/60/120/240-second backoff; the fifth failed attempt becomes terminal. Permanent SMTP rejection is terminal immediately. A crash leaves its lease recoverable; the next claimant marks the old attempt interrupted and uses a new token. Stale acknowledgements cannot overwrite another claimant's state. If SMTP succeeded but acknowledgement could not be confirmed, the job remains uncertain until lease recovery. Shutdown stops new admission, drains bounded admitted sends, and disconnects. Forced termination relies on lease recovery.

This is **at-least-once attempt semantics, not exactly-once SMTP or inbox delivery**. A crash/process pause around SMTP acceptance and DB acknowledgement may produce duplicate capture after retry. Stable per-event Message-IDs aid investigation but do not guarantee recipient-side deduplication. Finite retry limits intentionally leave failed work visible rather than retrying forever. There is no automatic replay or manual resend feature in this phase.

Disabling a preference cancels pending mail and preserves incident/event/attempt history. A claimed job rechecks opt-in before sending. An already in-flight SMTP request cannot be recalled; if it is accepted, history truthfully records SMTP acceptance even if the preference was disabled meanwhile. No UI promises instantaneous cancellation of remote side effects.

## Mailpit restriction and external email safety

The dispatcher requires **all** of `NODE_ENV=development`, `ENABLE_EMAIL_DISPATCHER=true`, `EMAIL_DELIVERY_MODE=mailpit`, and a dedicated local database. `watchtower_test` additionally requires the existing disposable confirmation. It opens no management port and does not use browser sessions or hardcoded account credentials.

The sender uses Nodemailer with a literal `127.0.0.1:1025` socket, no SMTP authentication, no proxy/service/transport URL, no redirects, plain text only, and file/URL content access disabled. Configuring another Mailpit host/port is refused. [Nodemailer's SMTP options](https://nodemailer.com/smtp) document these transport timeouts and content restrictions.

Recipients are fixed local test addresses: `watchtower+<owner UUID>@example.test`; the sender is `watchtower@example.test`. **Account email addresses are never used.** No recipient field exists in the settings API. No notification is sent to an unverified external address, and there is no external delivery mode. Templates contain the actual snapshotted endpoint name, check timestamp, HTTP status, response time, safe errors, incident/check IDs and up to 20 recorded differences. Header/control characters are sanitized; large field paths are truncated and additional changes are identified as omitted. Full recorded differences remain in authenticated monitoring history. Messages are bounded to 16 KiB.

History says **“SMTP accepted (Mailpit)”**, never “delivered.” An enabled preference is not proof that Mailpit or the dispatcher is running. The localhost Mailpit process is trusted developer infrastructure; the sender cannot prove what software owns port 1025. Do not configure Mailpit forwarding/relaying. Its shared debug UI is **not an isolated inbox per Watchtower user**; anyone trusted with access to that local tool can inspect captures. Watchtower's own settings/history remain owner-isolated. Neither service is approved for public exposure.

## Authenticated interface and dashboard

All new routes inherit existing localhost/Host/Origin/forwarded-header restrictions, required `X-Watchtower-Local`, server sessions, JSON limits, and CSRF on writes. Another user's or unclaimed endpoint returns 404.

| Method/path | Contract |
| --- | --- |
| GET `/api/endpoints/:id/notification-settings` | `{endpointId,enabled,updatedAt}`; absent row means disabled with null version |
| PUT same path | Exact `{enabled:boolean,expectedUpdatedAt:string|null}`; stale version returns 409 |
| GET `/api/endpoints/:id/notifications?limit=50` | `{events:[...]}` with actual incident, check/differences, outbox state and bounded attempt history |

Preferences share the endpoint lock. Updates use a strictly increasing millisecond version derived from database time; even two updates in one millisecond cannot reuse a version. Event history additionally filters by both recorded owner and current endpoint owner. Internal lease tokens are never serialized in the user-facing history response. External recipient injection and extra request fields are rejected.

The compact endpoint panel requires deliberate saving and confirmation for enablement. It reloads saved configuration, blocks duplicate actions, handles stale conflicts without automatic resubmission, and distinguishes unavailable data from disabled settings or empty history. Native event details show real incident state and changes. It loads up to 50 events and displays up to 20 differences per event to keep DOM work bounded. There are no fake statistics, delivery claims, worker indicators or frontend timers that send email.

## Proposed database changes and preservation

The migration adds four enums and **five new tables only**:

- `NotificationPreference`: optional per-endpoint opt-in and monotonic version; no row means disabled.
- `Incident`: availability/schema episode, actual opening/closing checks, resolution and fingerprint.
- `NotificationEvent`: immutable observation, actual check relationship, owner and endpoint-name snapshot.
- `EmailOutbox`: unique event, persisted delivery state, retry time/count and lease.
- `EmailAttempt`: one uniquely numbered claim/attempt with safe result metadata.

It adds keys/indexes/foreign keys on these new tables, a partial unique index for open incidents, and CHECK constraints for closed-incident state, attempt bounds and lease/attempt lifecycle. Prisma cannot express all these constraints; retain the reviewed SQL in future migrations. The migration runs in a transaction with 2-second lock and 15-second statement timeouts. FK validation may briefly lock referenced tables and fails rather than waiting indefinitely.

**There are no new columns, updates, inserts, backfills, ownership changes, resets, truncations, drops or recreations of existing tables/databases.** Existing endpoint/check/schema-change/schedule/provenance/user/session rows are untouched. New relationships in the Prisma schema do not add columns to those old tables. Existing accounts and endpoints remain opted out through absence of preference rows. Old failures do not acquire retroactive incidents or emails.

## Windows Mailpit setup

Mailpit/Docker were not found on PATH and neither SMTP port 1025 nor UI port 8025 was listening during this phase. No Mailpit installation, Compose startup or actual SMTP capture is claimed.

1. Download a current Windows archive matching your CPU from the [official Mailpit releases](https://github.com/axllent/mailpit/releases), following the [Windows binary installation instructions](https://mailpit.axllent.org/docs/install/). Extract `mailpit.exe`, for example to `C:\Tools\Mailpit`. The helper requires a current release with the listed security flags.
2. From the repository root, start local capture:

```powershell
& .\scripts\start-mailpit.ps1 -MailpitPath 'C:\Tools\Mailpit\mailpit.exe'
```

The helper refuses inherited relay/forwarding settings, binds SMTP/UI to loopback, restricts recipients to generated `.test` addresses, restricts UI Host values, disables reverse DNS/version lookups, and stores captures in ignored `apps/web/artifacts/mailpit.db`. It disables capture auto-deletion. Stop with Ctrl+C. The official [runtime options](https://mailpit.axllent.org/docs/configuration/runtime-options/) describe the flags; this setup has not been exercised without an installed binary.

Open `http://localhost:8025`. Do not configure [SMTP forwarding](https://mailpit.axllent.org/docs/configuration/smtp-forward/) or [relaying](https://mailpit.axllent.org/docs/configuration/smtp-relay/). The helper checks environment names without printing credential values; use a clean terminal without such settings.

Optional Docker Desktop alternative (not exercised):

```powershell
docker compose -f compose.mailpit.yaml up -d
# Stop the capture service while retaining its dedicated volume:
docker compose -f compose.mailpit.yaml down
```

This separate Compose file does not start, alter or remove either PostgreSQL service/volume. It uses the official Mailpit development image, host-loopback mappings, a dedicated capture volume and no relay configuration. Docker's `$$` in the recipient regex becomes a literal `$` inside the container. For repeatable infrastructure, choose a reviewed release/digest instead of the mutable development image tag.

**After migration approval and successful application only**, start the dispatcher in its own terminal:


## Remaining security and reliability limits

This is local capture, not verified external email delivery. A future separately approved phase must establish account email control with short-lived, one-time, hashed verification tokens, rate limits and re-verification after address changes; monitoring mail must remain disabled for external addresses until verified. Provider/TLS/credentials, bounce/complaint handling, consent and a production security review must precede any external transport. No verification token model, external sender, delivery webhook, public deployment or subsequent phase was implemented here.

Mailpit's shared local debug UI is outside Watchtower's per-user authorization boundary. Process crashes around SMTP may duplicate capture, and terminal failures have no resend control. Disabling cannot recall in-flight mail. Incident history is forward-only; schema observations retain the comparison engine's sample/array/optional-field limits. Existing process-local login limiting and localhost HTTP cookie exceptions remain documented Phase 6A limitations.
